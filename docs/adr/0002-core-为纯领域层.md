# `core` 是纯领域层，不允许依赖数据访问

`core` 此前既放领域逻辑又直连数据库（`core/data_loader.py` 导入 `db.donors_repo`，`core/preference/pipeline.py` 在函数体内 lazy import `db.pg` 拼 SQL），同时 `db/match_runs_repo.py` 反向导入 `core` 的领域类型，形成双向依赖。我们决定把依赖方向定为单向：**`db` 可以依赖 `core` 的领域类型，`core` 不得导入 `db`。**

## 为什么

另一个选项是承认 `core` 其实是"匹配算法工具箱"、允许它读库，反过来禁止 `db` 依赖它。但 `db/match_runs_repo.py` 已经在使用 `MatchSnapshotItem`、`RankedCandidateRef` 这些领域类型，走那条路需要把这些类型搬一次家，等于要改两个方向的依赖；而本决定只需要断掉一个方向。仓储层依赖领域类型本身是正常的分层形态，不需要修正。

顺带的收益是可测性：`core` 一旦不碰数据库，它的领域逻辑就能在不起 Postgres 的情况下测。

## 代价

硬过滤 SQL 生成已从 `core/preference/sql_filter.py` 下沉到 `db/hard_filter.py`，`core/data_loader.py` 的查询已移进 `db/donors_repo.py`。lazy import 不算合规的规避手段——用函数内导入绕过环，只是把违规藏起来，问题原样保留。
