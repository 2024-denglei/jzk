# 管理端与客户端是两个独立的前端应用

前端此前是单个 SPA：管理端通过客户端的路由挂载（`pages/AdminPage.tsx` 静态导入 13 个 admin 模块），因此约 2000 行管理端逻辑——用户列表、审计、管理员 CRUD、权限表、操作申请审批——会打进普通用户拿到的 bundle。我们决定拆成 `frontend/client/` 与 `frontend/admin/` 两个独立构建产物，共享代码放 `frontend/shared/`。

## 为什么

主要理由不是整洁，是**管理端源码不应下发给终端用户**。仅做懒加载（把管理端切成独立 chunk）解决不了这一点：chunk 一样能被下载和阅读。

拆分的成本恰好很低，因为两端在代码上已经几乎分开了：管理端向客户端一共只有 3 处导入，全是从 `src/types.ts` 取类型；它自带 `adminApi.ts` 做请求封装与 token 管理，不共用 `lib/api.ts`，也不共用 `AuthContext`。这与身份模型一致——管理员和用户是两套彼此独立的身份，不共用登录（见 `CONTEXT.md`）。

那唯一的类型共享点由 API 契约自动生成接管：生成产物落在 `frontend/shared/`，两端各自引用。

## 代价

需要引入 npm workspaces，Dockerfile 要构建两个前端产物，后端要挂载两个 SPA 入口。`frontend/shared/` 存在被滥用成"什么都往里塞"的风险——它的定位是生成的契约类型和极少量共用 UI，不是公共工具箱。
