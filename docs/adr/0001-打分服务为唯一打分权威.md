# 打分服务是唯一的打分权威

同一个神经网络此前存在两份实现：`services/match_scorer/` 的 HTTP 服务，和 `core/preference/v2/` 的进程内副本，各自维护一份网络定义与配置。我们决定打分服务是唯一的打分权威，进程内副本删除，访问入口是 `jzk.domain.preference.scoring_client`。第 7 步把打分服务收进 `backend/jzk/scorer/`，检查点放在 `backend/checkpoints/`。

进程内副本已于结构收敛第 5 步删除：`core/preference/v2/`、`v2_ranker.py`、`v2_adapter.py` 与权重 `models/best_model_v2.pt` 一并移除，选择后端的 `MATCH_SCORING_BACKEND` 开关也去掉了——留一个只有单一取值的开关会让人以为还能切回去。`tests/preference/test_scoring_authority.py` 守住这个不变量：打分服务之外的生产代码不得导入 torch，`backend/checkpoints/` 下不得出现第二份权重。

## 为什么

两份网络定义并行演进，最终一定会产出"同一份偏好画像、同一个候选，线上和离线分值不一致"的缺陷。这类缺陷没有报错、没有堆栈，只表现为结果看起来不太对，是最难定位的一类问题。而消除它的代价只是删掉一份副本。

选择保留 HTTP 服务而不是保留进程内副本，是因为服务侧已经被当作正式组件对待：有 `/healthz`、`/readyz`、`/metrics`，有 `model_manifest.py` 对检查点做 SHA256 身份校验，有独立的测试目录。进程内副本的注释自己写明了它是副本。

## 代价

- 每次匹配多一次网络往返。这是明知的成本，换取的是打分逻辑只有一处。
- 打分服务不可用时匹配整体不可用，因此必须有显式的降级或快速失败策略，不能靠"退回本地推理"兜底——那等于把删掉的副本请回来。
- 离线评测与线上必须共用同一个检查点，不允许为了方便另起一份加载路径。

## 已知偏离：目前与主应用共用镜像

"独立的打分权威"目前只做到了**独立进程**，没有做到独立交付：`compose.yml` 里 `scorer` 用的是和 `app` 完全相同的镜像，只换了启动命令，两个 worker 也是如此。因此打分服务的镜像里装着它并不需要的 `pandas`、`psycopg`、`openai`。

这是有意的临时状态。拆成独立镜像需要第二套依赖锁、第二个镜像、第二条流水线。在此之前，不要把「共用镜像」当成「打分可以退回进程内调用」的依据——那是本决定明确排除的选项。
