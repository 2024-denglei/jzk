# 筛选与匹配是两项独立能力

`/api/search`（用户自己指定条件、不经顾问、不经模型）与匹配（偏好画像 → 模型打分 → 匹配快照）此前共用 "matcher" 一套命名，看起来像同一件事的两种实现。我们决定它们是**两项独立能力**，各自保留实现，用词严格分开（见 `CONTEXT.md` 的「筛选」与「匹配」）。

## 为什么

让筛选改走打分服务，会把一次廉价的 SQL 条件查询变成一次模型推理：延迟和成本都上去，换来的只是"代码路径少一条"。两者的需求本就不同——筛选要低延迟、稳定分页、结果可复现；匹配要语义理解和个性化排序。

真正需要修的不是"有两套实现"，而是"两套实现都叫 matcher"，这个命名让人误以为它们应该合并。

## 代价

- `jzk.domain.screening` 与 `jzk.domain.screening_rank`（原 `core/matcher.py`、`core/ranker.py`）**不是死代码**，前端筛选页在用（经 `/api/search`）。不得以"统一到打分服务"的名义删除。
- 两套排序逻辑并存是有意的。代价是筛选名次与匹配名次**不可比**，界面上不应把两者混排，也不应声称它们出自同一口径。
