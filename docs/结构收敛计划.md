# 结构收敛计划

一份有生命周期的工作文档：记录这轮结构治理**按什么顺序做、做到哪了**。为什么这样定不写在这里，写在 `docs/adr/`；用词不写在这里，写在 `CONTEXT.md`。全部步骤完成后本文件应当删除，而不是留下来慢慢过期。

## 起因

项目积累了五类结构问题，其中三类已经在实际造成缺陷：

1. **仓库边界错位**：真正的 git 仓库在 `jzk/`，但工作区开在上一层，那里的 `.git` 是个空目录，导致根目录的 `AGENTS.md` 有一份不在版本控制里。
2. **一个概念四套实现**：打分同时存在旧 DataFrame 路径、启发式路径、进程内模型推理、模型微服务四条代码路径，其中后两者各自维护一份网络定义。「画像」有 7 种表示。
3. **分层名字不符实**：`core` 直连数据库；`api` 与 `dialogue`、`db` 与 `dialogue` 之间存在真实的导入环，且用函数内 lazy import 绕过；`models/` 目录里没有一个 `.py`。
4. **文档描述已死的架构**：`docs/` 下的架构图仍在描述零引用的 `dialogue/response_gen.py`，而应用还挂着 `GET /architecture` 把它对外提供。
5. **配置自相矛盾**：PORT、Postgres 端口、打分服务 token 名、数据文件路径各有两处不一致的定义。

## 半径

**全面收敛**：连领域词汇、目录命名、前后端契约生成方式一起重做。明确排除的范围见文末。

### 各步骤的具体动作

**第 3 步 依赖锁（已完成）**：`requirements.txt` 与 `pytest.ini` 已被 `pyproject.toml` + `uv.lock` 取代，`pytest`、`PyYAML` 归入 `dev` 依赖组，不再进入运行镜像。torch 钉到 `==2.14.0` 并只从 CPU 专用源取——检查点内只有序列化协议版本、无法考据产出它的 torch 版本，所以真正要保证的是**所有环境用同一个构建**。`requires-python` 收紧到 `>=3.12,<3.13` 并加 `.python-version`：放宽上界时 uv 会在开发机上挑 Python 3.14，于是本地测 cp314 的 wheel、线上发 cp312 的。Dockerfile 与 CI 都改用 `uv sync --locked`，改了 `pyproject` 却忘记重新锁定会直接失败而不是静默装出另一套依赖。

**第 4 步 配置（已完成）**：原则是**关键配置不给默认值，宁可启动即失败**。PORT 统一 8010；打分密钥合并为唯一变量名 `SCORER_TOKEN`（主应用曾读 `MATCH_SCORER_TOKEN`、服务端读 `SCORER_TOKEN`，两者默认值相同所以本地永远是通的，只在生产只改一处时才暴露成 401，而那条路径是降级可用的，故障会伪装成「匹配结果为空」）；删除与 `compose.yml` 重复的 `db/postgres/docker-compose.yml`（它同样占用 `jzk-postgres` 这个 container_name，且发布 5432 而根目录发布 5433）；`DATA_FILE_PATH` 整个从配置层移除，灌库脚本改为 `--file` 必填；`DATABASE_URL` 去掉内置的开发凭证默认值，改由 `validate_database_config()` 在任何环境启动时强制要求。

删掉那份重复的 Compose 时有个不显眼的约束：它的卷是匿名声明的，而它所在目录名为 `postgres`，于是 Compose 把卷命名为 `postgres_jzk_pg_data`——这正是根 `compose.yml` 里 `name: postgres_jzk_pg_data` 的来由，是为了继承旧数据而留的兼容写法。删文件安全，改卷名会让现有数据脱钩。

配置漂移这类缺陷不改变行为、只是连不上或鉴权失败，因此新增 `tests/test_config_consistency.py` 把「同一件事写了两遍」钉在一起：应用端口在 config、`.env.example`、compose、Dockerfile、Vite 五处必须同为 8010；`.env.example` 里的连接串端口必须等于 compose 实际发布的端口；打分密钥只允许一个变量名；整套服务只允许一份 Compose 定义。

**第 5 步 打分收敛（已完成）**：删除 `core/preference/v2/`（786 行）、`v2_ranker.py`、`v2_adapter.py` 与权重 `models/best_model_v2.pt`，`scoring_client.py` 成为唯一入口。选择后端的 `MATCH_SCORING_BACKEND` 与 `V2_CHECKPOINT_PATH`/`V2_CONFIG_PATH`/`V2_FORCE_CPU` 一并删除：进程内那条通路没了以后，留一个只有单一取值的开关只会让人以为还能切回去。快速失败策略本来就已经在位——`api/match.py` 与 `dialogue/generation_processor.py` 把 `RankerUnavailable` 映射成 503，这一步只是拿掉了「退回本地推理」这个选项。

删除过程中发现 `v2_adapter.profile_to_v2_spec` 与 `scoring_client.profile_to_scoring_spec` 是同一段逻辑的两份拷贝，且**已经漂移**：keyword 字段一份发 `match_mode`、另一份发 `match`。这正是 ADR 0001 所说那类缺陷的实证——两份实现给出不同的请求体，不报错、没堆栈。`v2_adapter` 剩下的 `donor_row_to_v2` 是打分契约的字段归一化，已并入 `scoring_client.normalize_donor_row`。

删完之后 torch 在主应用里已无使用者，只剩 `services/match_scorer/`。它仍在 `pyproject.toml` 里，因为两者共用镜像（见 ADR 0001 的「已知偏离」）。

**第 6 步 解耦（已完成）**：编排层放在 `matching/`（第 7 步才会收进 `backend/jzk/`）。`execute_match` 从 `api/match.py` 抽出，HTTP 与对话都只调它、互不 import；分页游标一并从 `api/match_cursor.py` 挪到 `matching/cursor.py`，否则编排层再 import api 会立刻形成新环。`match_profile` 不再自己查库：`fetch_rows`/`count_rows` 吃的是画像，缺注入就 TypeError。硬过滤 SQL 下沉到 `db/hard_filter.py`，`load_donor_data` 移进 `db/donors_repo.py`。密码哈希抽到顶层 `passwords.py`，`db.pg.bootstrap_admin` 不再碰 `api.auth_utils`。handler 里的 SQL 收进 `users_repo` / `user_records_repo` / `admin_admins_repo`。

拆环时还发现第三道：`db.generation_runs_repo` 为了序列化状态去 import `dialogue.state_schema`，而 dialogue 本来就 import 这个仓储。状态类型已经在 `db.chat_models`，dump 不必绕去 dialogue。守卫测试 `tests/test_layering.py` 扫的是源码 AST，函数内 lazy import 也会被抓住。

**第 7 步 改名（已完成）**：后端收进可安装包 `backend/jzk/`，导入一律 `from jzk...`，去掉 `pythonpath=.`。`core`→`domain`、`models`→`backend/checkpoints`、`services/match_scorer`→`backend/jzk/scorer`、`core/matcher.py`/`core/ranker.py` 按实际职责改名为 `screening`/`screening_rank`、`db/chat_models.py`→`chat_contracts`；`dialogue` 按 `CONTEXT.md` 拆成 `chat/`（对话存储与查询）与 `advisor/`（顾问与生成）；顶层散落的 `main.py`、`config.py`、`redis_client.py`、`password_policy.py` 一并收入包内。前端目录 `web/` 改名为 `frontend/`（拆成 client/admin 是第 8 步）。compose 仍在仓库根，镜像入口改为 `jzk.main:app` / `jzk.scorer.app:app`。

**第 8 步 契约与前端（已完成）**：对话查询挂上已有的 Pydantic `response_model` 后，从 live FastAPI schema 导出 `frontend/shared/openapi.json`，再用 `openapi-typescript` 生成 `openapi.d.ts`。CI 后端核对 JSON 等于当前应用，前端核对生成物没有手改。前端按 npm workspaces 拆成 `client/`、`admin/`、`shared/` 三个包；管理端源码不再进入用户 bundle。后端挂两个 SPA：客户端 `/`，管理端 `/admin/`（Vite `base: '/admin/'`，Router 不设 basename，好让现有 `/admin/users` 路径继续匹配）。`shared/` 只放生成契约和一层旧名字别名，没有把 `lib/api` 抽进去。冻结匹配页仍是手写类型——OpenAPI 里还是松的 `dict`。

## 沿途发现的缺陷

同一个模式反复出现：**镜像里能跑、开发机上能跑，但从声明的源头装就是坏的**。

- 对话灰度开关默认关闭，而 v1 存储已被迁移脚本删除，任何不携带完整 `.env` 的部署一上线对话就 503 且无处回退。`.env.example` 里两个开关正是 `0`。已修（第 1 步）。
- `httpx` 是 `api/match.py` 与 `core/preference/scoring_client.py` 的直接依赖，却从未出现在 `requirements.txt`，靠 Dockerfile 里一条额外 `RUN` 补上；而当前 openai SDK 依赖的已是 `httpx2`，不再顺带装它。已修（`f61a2d2`）。
- `.env` 的 `DATABASE_URL` 指向 `127.0.0.1:5432`，而 postgres 容器实际发布 5433。在 Docker 外跑应用会连不上库。已修（第 4 步）；同一串错误端口还内置在 `config.py` 的默认值里，一并去掉了默认值。
- 主应用与打分服务用两个不同的环境变量名承载同一个共享密钥，只改一处即在运行时鉴权失败。已修（第 4 步）。

## 明确不做的事

- **前端巨型组件拆分**。`BranchingChatPanel.tsx`(843 行)、`DonorsPage.tsx`(716 行)、`FilterPanel.tsx`(479 行) 暂不动。它与后端结构收敛没有依赖关系，混做会让每个改动都又大又难 review；更实际的顾虑是前端测试全是 utility 与 state 单测，没有任何 DOM 或组件测试，拆这类交互组件缺少护栏。
- **打分服务独立镜像**。目前它与主应用共用镜像、只换启动命令，因此背着并不需要的 `pandas`、`psycopg`、`openai`。这是有意的临时状态，理由见 ADR 0001 的「已知偏离」一节。
- **让筛选走打分服务**。见 ADR 0003。

## 已知环境问题

本机 `127.0.0.1:7890` 上的代理处于「在监听但破坏 TLS」的状态：直连 github.com 返回 200，经代理返回 000。而 git 配置里设了 `http.proxy` / `https.proxy` 指向它，于是 `git push`、`gh`、`pip install` 全部失败，且报错信息误导性极强（`gnutls_handshake() failed`、`token is invalid`）。绕过代理即可恢复。这是开发机问题，不在本计划范围内，记在此处避免重复排查。
